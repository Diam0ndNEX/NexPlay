## Rules
- (8.2.3) No source file outside `NexPlay/Windows/BCD` may share a file name with one inside it: engine builds compile both into one target and Xcode stops with "filename used twice". The first engine build (Windows runtime release present since 2026-11-14) failed on JITPairing.swift and Onboarding.swift; NexPlay's copies were renamed. Check with `comm -12` on both basename lists before adding a file.
- Codable fields added to `Game` must be optional or have a default, so old libraries still load. An unreadable `library.json` is copied aside before anything overwrites it. (Prefer optionals: synthesized Decodable ignores defaults and requires the key.)
- Keep every `switch` on `GameEngine` exhaustive (Models, ImportPipeline warnings). Same for `RuntimeKind` and `NexSettingsPage`.
- **How a game runs is decided by `GameRuntimes` (Runtimes.swift).** Don't add new `isRuby`/`isWebGame` branches in screens to pick a player; add a `GameRuntime` or a `RuntimeCapabilities` flag. (8.4.0) Game page and Game Settings sections follow `RuntimeCapabilities` too.
- Compare resolved paths when computing relative paths (iOS reports `/var` as `/private/var`).
- Never lose a save: atomic writes; back up before restoring, deleting saves or migrating; replaced files become `.nex-displaced.bak`; deleting a game rescues its save files first.
- Do not override `navigator.getGamepads`: physical controllers reach the game through the Gamepad API too (Empo disables it; NexPlay does not).
- **The NW.js shim's `process.versions` must not contain `node`**: Emscripten code (MZ's Effekseer, some plugins) then thinks it is in Node.js, reads `__dirname` and the game stays black. Empo leaves `versions` empty.
- New settings keys go in the `SettingsKey` extension of the file that uses them, get a default in `NexPlayApp.defaultSettings`, and join a key list Reset clears (`all`, `playerKeys`, `backgroundKeys`, `jitKeys`). Per-game Play Assist / Game Tools options are not settings keys: they live in `SaveStates/<game-uuid>/options.json` (`AssistOptions`, decoded with decodeIfPresent so new fields need a default there).
- Message handlers: `nexStats`, `nexLog`, `nexExit`, `nexSize` (sent, not handled yet), feature handlers (`nexTranslate`). Remove each in `shutdown()`.
- Write boring, explicit Swift for iOS 18 (8.0.0; was 16) (nothing is compiled before pushing). Re-read changed files for imports, labels, `self.` and `@MainActor` mistakes. Never write `let x = x(...)` where `x(...)` is a method of the same type (Swift reports the local as used before its declaration). Never pass `&array` and `array.count` in the same call (overlapping access error): read the count first. `MainActor.assumeIsolated` is iOS 17+: don't use it.
- Use `GameLog` for game problems and `AppLog` for app problems. JIT steps are logged to AppLog with a `jit:` prefix (6.3.0+).
- Pickers (7.13.3): never allow folders and files in one picker (`.folder` with `.zip`/`.item`): "Open" then opens a picked ZIP as a folder and nothing is imported. Ask which kind first, or use two entries. One `fileImporter` per view hierarchy level: two (even one inside a Form section and one outside) don't both work; switch the content types with a mode state that the completion reads (don't clear the mode in the isPresented binding).
- Cheat engine (7.13.3): read game values raw (`$gameVariables._data`, `$gameSwitches._data`, `$gameParty._items/_weapons/_armors/_gold/_actors`, actor `_hp/_mp/_level`), never through value()/numItems(): plugins compute some of them with scripts that throw outside their scene and left the game on its error screen after the engine closed.
- SwiftUI: don't present a confirmation dialog or alert from a `fileImporter` completion right away; it is lost while the picker closes. Act directly (with a backup) or present after a delay.
- Push files that depend on each other in one commit (6.0.0 went out as two commits, the first of which can't build on its own).
- New in-game tools go into the Game Panel (a card in `GamePanelView`, actions on the owning feature), not into new game-menu submenus.
- 7.0 rules (SPEC-7.0 section 13): Windows games never write outside their prefix and game folder; JIT code paths must work without JIT (fallback messages); iOS apps can't fork/exec, so never call `posix_spawn` (Wine runs as threads in NexPlay's process, as in BCD).
- JIT (6.3.0): one script only (`JITScript.source`, BCD's madeira-jit.js) for the helper and StikDebug; never a user setting. Never execute BRK #0xf00d unless the trap handler is installed and a debugger with that script is attached (P_TRACED): an unanswered BRK with a plain debugger stops the thread for good. The pairing file stays in the Keychain and is never logged. StikJIT stays out of the app binary (only the helper links it).

## Decisions
- 8.0.0 (BCD merge, docs/PLAN-8.0.md): BCD's app code is NexPlay source (NexPlay/Windows/BCD), not a library with its own screens. Rules: (1) NexPlay files that name BCD types do it inside `#if NEXPLAY_WINDOWS` (builds without the engine don't compile the BCD folder); (2) changes to BCD files are listed in `NexPlay/Windows/BCD/NEXPLAY-CHANGES.md` with a date (BCD's terms 4(c)2) and the file gets the one-line "Modified for NexPlay" note; keep BCD's headers; (3) a BCD type whose name NexPlay also uses gets a BCD prefix (both are one Swift module); (4) Wine runs once per app run (BCD's rule): a second Windows game asks for a restart; (5) owner's decision 2026-11-13: BCD's Steam/GOG/Epic/EA/Dock code stays compiled and untouched but hidden (no screen shows it; only itch.io is shown), so BCD updates stay easy to merge; change BCD files as little as possible in every step. BCD's own front-end screens stay unreachable too (8.7.2 checked: every one is still named by another BCD file, so none was deleted); (6) one Windows game per app launch stays (iOS can't start a new process, so only quitting resets Wine); ideas around it are in docs/PLAN-8.0.md. BCD's helper-memory extension (MadeiraMemoryHost, opt-in mempool-mb) is NexPlayMemoryHost since 8.6.4 (its only entitlement, get-task-allow, fits the owner's profile).
- 6.3.0 (built-in JIT): copied BCD's architecture: a classic app extension (`com.apple.ar.viewer` point, started by bundle ID through the private NSExtension API) runs StikJIT 2.0.1 (MPL-2.0 release XCFramework, idevice inside) because a process can't debug itself; the request is JSON in the extension item; `enable` lasts until the script detaches. NexPlay waits for P_TRACED, then calls `nexjit_selftest` (debugger `_M` RX page + vm_remap RW alias = BCD's strategy 2, what BCD's FEX pool does) and `nexjit_detach`. The script is BCD's madeira-jit.js so 7.0's BCD FEX/Wine works without another script; 7.0 replaces the test page with BCD's pool request (StikJITHelper.allocatePool) and keeps the debugger attached while Wine runs (Wine needs it to prepare PE code pages). Revisit after JIT works on the device (owner's profile grants packet-tunnel-provider). Not built from BCD: on-device pairing (iOS 27 OnDevicePairing), the JIT shortcut, the no-debugger pool (iOS 18/non-TXM), JIT method picker.
