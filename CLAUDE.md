Personal iPhone game player for RPG Maker MV/MZ and HTML5 games (SwiftUI + WKWebView, iOS 16+), with RPG Maker XP/VX/Ace through the mkxp-z core in builds that turn on `NEXPLAY_MKXP`.
Not a general web browser: everything in here is treated as a game. Version 6.3.0 (build 36). Engines: RPG Maker MV/MZ, HTML5, Godot (Web exports and desktop .pck/.exe), Ren'Py (RenPyWeb), Flash (Ruffle), Construct, Twine, TyranoScript; XP/VX/Ace with the mkxp core.

**Read `docs/SPEC.md` for the plan, `docs/RESEARCH.md` for what the reference apps do. Paste-ready prompt for new chats: `docs/PROMPT.md`.**

## How the owner works
- iPhone only (iPhone 17 Pro Max, iOS 27+), no Mac or PC. GitHub Actions builds an unsigned IPA; the owner signs it with their own development certificate.
- Swift can't be compiled in the Claude environment. If the Actions build fails, the owner pastes the red error lines; fix the first error first.
- Push source changes straight to `main`.
- `.github/workflows/*` can't be pushed from Claude. Give the owner the full file to paste on github.com. The current workflows are `docs/workflow-6.4.0.yml` (build.yml: newest Xcode, StikJIT fetch, Windows runtime merge, ldid) and `docs/workflow-windows-runtime.yml` (build-windows-runtime.yml, manual).
- **Bump the version on every push**, without being asked: `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in `project.yml`. Patch for fixes, minor for features, major for big changes.
- The old NexHTML repo is left untouched.
- Keep replies short: what changed and what the owner must do, if anything.
- The owner compares with RPGPlayer screenshots (ideas only) and Empo (code may be copied).

## Layout
- `project.yml`: XcodeGen config (the Xcode project is generated in CI, never committed). Links the system libarchive (`-larchive`) and uses `NexPlay/NexPlay-Bridging-Header.h`. `CODE_SIGN_ENTITLEMENTS` = `NexPlay/NexPlay.entitlements` (6.2.0). 6.3.0: second target `NexPlayJITHelper` (app-extension, iOS 17.4, sources `NexPlayJITHelper/` + `NexPlay/JIT/JITRequest.swift`, links `vendor/StikJIT/StikJIT.xcframework`, weak ExtensionFoundation, runpath `@executable_path/../../Frameworks`); the app embeds the helper (PlugIns) and StikJIT.framework (Frameworks, not linked: the app stays iOS 16).
- `NexPlay/NexPlay.entitlements` (6.2.0/6.2.1): get-task-allow, increased-memory-limit, increased-debugging-memory-limit, extended-virtual-addressing. - `NexPlayJITHelper/` (6.3.0): `NexPlayJITHelper.swift` (principal class `NexPlayJITHelperHandler`, one request at a time on a serial queue: prepare = `StikJIT.prepareDevice`, enable = `StikJIT.enableJIT(targetPID:pairingFile:ddiPaths:script: .customBase64, forceScript: true)` which returns when the script detaches, resetDDI; DDI cache in the helper's Library/StikJIT; the pairing data is written to a temp file and deleted), `Info.plist` (XPC! bundle, NSExtension point `com.apple.ar.viewer`, as BCD), `NexPlayJITHelper.entitlements` (get-task-allow, written by ldid). ## Rules
- Codable fields added to `Game` must be optional or have a default, so old libraries still load. An unreadable `library.json` is copied aside before anything overwrites it. (Prefer optionals: synthesized Decodable ignores defaults and requires the key.)
- Keep every `switch` on `GameEngine` exhaustive (Models, ImportPipeline warnings). Same for `RuntimeKind` and `NexSettingsPage`.
- **How a game runs is decided by `GameRuntimes` (Runtimes.swift).** Don't add new `isRuby`/`isWebGame` branches in screens to pick a player; add a `GameRuntime` or a `RuntimeCapabilities` flag.
- Compare resolved paths when computing relative paths (iOS reports `/var` as `/private/var`).
- Never lose a save: atomic writes; back up before restoring, deleting saves or migrating; replaced files become `.nex-displaced.bak`; deleting a game rescues its save files first.
- Do not override `navigator.getGamepads`: physical controllers reach the game through the Gamepad API too (Empo disables it; NexPlay does not).
- **The NW.js shim's `process.versions` must not contain `node`**: Emscripten code (MZ's Effekseer, some plugins) then thinks it is in Node.js, reads `__dirname` and the game stays black. Empo leaves `versions` empty.
- New settings keys go in the `SettingsKey` extension of the file that uses them, get a default in `NexPlayApp.defaultSettings`, and join a key list Reset clears (`all`, `playerKeys`, `backgroundKeys`, `jitKeys`). Per-game Play Assist / Game Tools options are not settings keys: they live in `SaveStates/<game-uuid>/options.json` (`AssistOptions`, decoded with decodeIfPresent so new fields need a default there).
- Message handlers: `nexStats`, `nexLog`, `nexExit`, `nexSize` (sent, not handled yet), feature handlers (`nexTranslate`). Remove each in `shutdown()`.
- Write boring, explicit Swift for iOS 16 (nothing is compiled before pushing). Re-read changed files for imports, labels, `self.` and `@MainActor` mistakes. Never write `let x = x(...)` where `x(...)` is a method of the same type (Swift reports the local as used before its declaration). Never pass `&array` and `array.count` in the same call (overlapping access error): read the count first. `MainActor.assumeIsolated` is iOS 17+: don't use it.
- Use `GameLog` for game problems and `AppLog` for app problems. JIT steps are logged to AppLog with a `jit:` prefix (6.3.0+).
- SwiftUI: don't present a confirmation dialog or alert from a `fileImporter` completion right away; it is lost while the picker closes. Act directly (with a backup) or present after a delay.
- Push files that depend on each other in one commit (6.0.0 went out as two commits, the first of which can't build on its own).
- New in-game tools go into the Game Panel (a card in `GamePanelView`, actions on the owning feature), not into new game-menu submenus.
- 7.0 rules (SPEC-7.0 section 13): Windows games never write outside their prefix and game folder; JIT code paths must work without JIT (fallback messages); iOS apps can't fork/exec, so never call `posix_spawn` (Wine runs as threads in NexPlay's process, as in BCD).
- JIT (6.3.0): one script only (`JITScript.source`, BCD's madeira-jit.js) for the helper and StikDebug; never a user setting. Never execute BRK #0xf00d unless the trap handler is installed and a debugger with that script is attached (P_TRACED): an unanswered BRK with a plain debugger stops the thread for good. The pairing file stays in the Keychain and is never logged. StikJIT stays out of the app binary (only the helper links it).

## Decisions
- 6.3.0 (built-in JIT): copied BCD's architecture: a classic app extension (`com.apple.ar.viewer` point, started by bundle ID through the private NSExtension API) runs StikJIT 2.0.1 (MPL-2.0 release XCFramework, idevice inside) because a process can't debug itself; the request is JSON in the extension item; `enable` lasts until the script detaches. NexPlay waits for P_TRACED, then calls `nexjit_selftest` (debugger `_M` RX page + vm_remap RW alias = BCD's strategy 2, what BCD's FEX pool does) and `nexjit_detach`. The script is BCD's madeira-jit.js so 7.0's BCD FEX/Wine works without another script; 7.0 replaces the test page with BCD's pool request (StikJITHelper.allocatePool) and keeps the debugger attached while Wine runs (Wine needs it to prepare PE code pages). StikDebug fallback sends the script as `script-data`. **Tunnel: NexPlay relies on LocalDevVPN, not its own packet tunnel**: an own tunnel is a second extension that needs the network-extension entitlement in its own profile plus a VPN configuration, so it adds a signing failure point before JIT is even proven; StikJIT and BCD are built and tested against LocalDevVPN (10.7.0.1). Revisit after JIT works on the device (owner's profile grants packet-tunnel-provider). Not built from BCD: on-device pairing (iOS 27 OnDevicePairing), the JIT shortcut, the no-debugger pool (iOS 18/non-TXM), JIT method picker.
- 6.3.0 CI: the workflow selects the newest non-beta Xcode on the runner (StikJIT's interface needs a recent compiler) and `tools/fetch_stikjit.sh` falls back to building StikJIT from source with that Xcode. The app's deployment target stays iOS 16; the helper is iOS 17.4.
- NW.js mode is on by default for MV/MZ; per-game override in Info & Settings. Save migration runs once per game, copies only, never overwrites an existing save file, reloads when it wrote anything.
- Browser-mode data (localStorage/IndexedDB) can't be rescued when a game is deleted; the dialogs say so.
- Backups are in `Backups/<game-uuid>/`; retention keeps the last 5/10/20 automatic ones, `before-*` safety copies are kept.
- "Show in Files" not added: data lives in Application Support; moving it to Documents would move every game. Use ZIP export.
- Controller defaults: A OK, B cancel, X menu, Y dash, L1/R1 page up/down, R2 fast forward, Menu = menu. "keys" mode also leaves the Gamepad API alone.
- Fast-forward button toggles 1× and `Game.fastForwardSpeed` (2-9, default 2); menu offers 1/2/3/4/6/9×.
- Hidden games are a UUID list in UserDefaults (`hiddenGames`), not `Game.isHidden`. Collections can be hidden too.
- Cheats are always in the game menu for MV/MZ; only numbers are passed to JS.
- 6.4.0: BCD is not copied file by file: its app target is built as a library (BCDCore.framework) by replaying BCD's own workflow, and NexPlay shows BCD's interface. Reason: the glue lives in BCD's app target and DXMT looks up its symbols at runtime from that target's export list. Never edit BCD's files in our repo; change tools/windows/patch_bcd_for_nexplay.py instead.
- 6.2.0: the 7.0 work starts with the runtime registry (no behaviour change), the entitlements + ldid step and Settings > Diagnostics. New `GameEngine` cases (.windows, .unity, ...) are added with the Windows runner (7.0.0), not before, so 6.x builds touch no engine switch. BCD's Windows support is spread over its whole app (WineProcessBridge.m ~260 KB, StikJITHelper.swift ~160 KB, JITAllocator.c, FEXBridge.mm, prefix-template.tar.gz, static libs in app/Madeira); its JIT helper and memory host are extra targets (MadeiraJITHelper, MadeiraMemoryHost). Read those before 6.4.0.
- 6.2.1: Steam/GOG dropped by the owner (docs/OWNER-ANSWERS-7.0.md): no Stores phase or flag (`NEXPLAY_STORES` removed from Diagnostics in 6.3.0).
- 5.0.0: save states are NexPlay's own (not the game's slots): no globalInfo, `_lastAccessedId` or Continue side effects, same code for NW.js and browser mode. Save states are deleted with the game (they are not rescued; real saves still are). The message log hooks `Window_Message.startMessage` (text through `Window_Base.convertEscapeCharacters`, escape codes stripped; MZ speaker name) and `Game_Message.onChoice`. Instant text forces `_showFast`/`_lineShowFast` in `updateShowFast`; auto-advance makes `Window_Message.isTriggered` true N seconds after `startPause`.
